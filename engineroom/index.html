The team: a kid, a grown-up and an AI helper

You don't need to know how to code. You need to know what you want, and to ask good questions.
Kid

The idea boss

  • Dreams up what to build and who it's for
  • Decides how it looks and feels
  • Tests it and tries to break it
Grown-up

The safety boss

  • Owns the accounts, passwords and money
  • Says yes before anything goes live
  • Keeps people's information private
AI helper

The builder

  • Writes the code from your ideas
  • Explains how it works, as many times as you ask
  • Fixes what breaks when you tell it what you saw
How a build session goes

The kid says what they want in their own words. The AI helper builds a preview. You both try it, the kid says what's wrong or what's missing, and the AI helper changes it. Repeat until it feels right. Then the grown-up puts it live.

The three parts of anything online

Games, recipe books and team sites all have these three. Pick a project to see them.
Frontend

What you see

Like the Minecraft world on your screen. It looks amazing, but it forgets everything if nobody saves it.

Server

The Worker

A small program that runs on Cloudflare's computers. The frontend sends it messages. It checks the rules, then saves or looks things up.

Like a redstone machine: something goes in, it checks it, and something comes out.

Database

D1

The database keeps things saved even when everyone closes the page. Only the Worker can open it.

Like a LEGO sorting box with labeled drawers. Each drawer is called a table.

Frontend and backend

The part you see is the frontend because it's in front. The Worker and the database are the backend because they're behind, hidden away. "Making a backend change" means changing the Worker, the database, or both.

3

A message's trip

Worked example: Quackers. What really happens when you find a duck. Press Next to follow it.
  1. 1You tap a hidden duck. The game shows the duck in your log right away.
  2. 2The game packs a message called a request. It says where it's going and what's inside.
    POST /api/ping {"pid":"tab-7k2q","ducks":13}
  3. 3The request flies over the internet to the Worker. pid is your device's random id. It's not your name.
  4. 4The Worker checks it. Is the id the right shape? Is this device sending too many messages this minute?
  5. 5The Worker saves it in the database with a line of SQL, the language databases speak.
    UPDATE players SET ducks=13 WHERE pid='tab-7k2q'
  6. 6The Worker sends back an answer called a response: {"ok":true}. Trip complete.
GET and POST

GET means "please tell me something", like asking how many friends joined. POST means "here's something new", like a duck you found. The messages are written in JSON, which is just labels and values inside curly brackets.

4

Tables: the drawers

Worked example: Quackers. Its friend link needed two new drawers.

A table has columns across the top (what kind of fact) and rows going down (one thing each). It's like a Minecraft chest where every slot has a label.

friends
codepidatjoins
q7mz4kfatab-7k2qday 02
hx2p9wdepho-3c4dday 00

One row per player who asked for a share code. joins counts friends who came with it.

referrals
pidat
new-8b1cday 0
new-5d7eday 0

One row per device that was counted as a friend. That's all.

Here's the real SQL that builds the friends drawer:

CREATE TABLE IF NOT EXISTS friends(
  code  TEXT PRIMARY KEY,         -- the random share code, never two the same
  pid   TEXT NOT NULL UNIQUE,     -- whose code it is, one code per player
  at    INTEGER NOT NULL,         -- when it was made
  joins INTEGER NOT NULL DEFAULT 0 -- how many friends joined, starts at 0
);
Save only what you need

Look at referrals again. It saves "this device was counted", but never who invited it. The game only needed to know "has this device been counted before?", so that's all it keeps. Every fact you don't save is a fact that can never leak. Great builders think about this first.

5

Routes: doors into the Worker

Worked example: Quackers. A route is a named door, and each one does one job.

A route is a method plus an address, like POST /api/friend/claim. The Worker has a list near the top that says which door goes to which job. These are the lines for the friend link in Quackers, made a little simpler:

if (r === "/api/friend/code"   && req.method === "POST") // give me my share code
if (r === "/api/friend/status" && req.method === "GET")  // how many friends joined?
if (r === "/api/friend/claim"  && req.method === "POST") // count me as a friend

The claim door has a guard with a checklist. A friend only counts when every box is true:

  • The share code is real.
  • It isn't your own code. No counting yourself!
  • The friend has found at least one duck.
  • The friend is new: their first visit came after the code was made, and only a few days ago.
  • This device was never counted before.
  • The sharer hasn't hit today's limit. This stops anyone from faking hundreds of friends.

When all six pass, the Worker adds a row to referrals and adds 1 to joins. When joins reaches 1, the game unlocks a bonus duck for the sharer.

Why does the guard live in the Worker?

Anyone can mess with the game on their own device, the same way people use cheat mods. The Worker runs on Cloudflare's computers, so only the people who run the game can change its rules. Any rule that keeps things fair has to live in the backend.

    Changing the real one
    The same steps every time, with a grown-up doing the ones that touch real accounts.
    
  
      
    
    • "The game should remember which world each player likes best." If it doesn't fit in one sentence, make it smaller.
      • 
    
    • Which table, which new columns, which route? What's the smallest amount you need to save? Try it in the practice room first.
      • 
    
    • Ask your AI helper to build the change as a preview. The real project stays the same until a grown-up says yes.
      • 
    
    • Try to cheat it: twice in a row, your own code, no ducks found. Quackers' friend link had 57 test checks before anyone pasted anything.
      • 
    
    • The grown-up opens the database's console in Cloudflare and pastes the SQL as one line. IF NOT EXISTS makes it safe to run twice. Drawers go in before the Worker tries to use them.
      • 
    
    • The grown-up opens the Worker, pastes the new code and presses Deploy.
      • 
    
    • Close and reopen it. Try the new thing. The grown-up checks the dashboard.
      • 
    
    • The date, what you added, and why. Future you will thank you.
      • 
  
    
  
    How to undo
    The Worker: Cloudflare keeps the older versions of the Worker, so the grown-up can switch back to the last one that worked.
    The database: adding a table or a column is easy to undo. Deleting is forever, so we never delete a table or a column with players' data in it without a backup and a grown-up's yes.
    
  
    Golden rules
    1. Preview first, live only with a grown-up's yes. 2. One change at a time. 3. Passwords and keys never go in the code; they live in Cloudflare's secret settings, and only the grown-up in charge knows them. 4. Save as little about players as you can. Privacy comes first, always.
